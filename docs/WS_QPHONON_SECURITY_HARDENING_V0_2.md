# WS-QPHONON Security Hardening V0.2\n\n## Claim boundary\n\nThe phrase 10x more secure is treated as an engineering target, not as a measured risk-reduction claim.\n\nV0.2 defines a ten-control hardening profile. Passing all ten controls means ten independent defensive barriers are machine-enforced or explicitly gated. It does not demonstrate that compromise probability is exactly ten times lower.\n\n## Ten enforced barriers\n\n1. Strict ECHO top-level event shape; unexpected fields are rejected.\n2. SHA-256 format for raw-data, configuration, prior-event, and event digests.\n3. Canonical JSON event digest; post-record mutation becomes detectable.\n4. Previous-event digest linkage; ordered evidence can be checked as a chain.\n5. UTC freshness window; stale or materially future-dated events are rejected.\n6. UUIDv4 event replay detection via a caller-maintained seen-ID store.\n7. Exact configuration-digest binding; evidence from a different configuration is rejected.\n8. PRIME numeric inputs must be real, finite, correctly typed, and in physical/risk ranges.\n9. PRIME success only reaches READY_FOR_HUMAN_APPROVAL; execution requires a separate verified approval attestation bound to experiment and config digests, with a one-time approval ID and expiry.\n10. QPHONON CI uses least privilege, disables persisted checkout credentials, requires no repository secrets, and pins third-party GitHub Actions to immutable commit SHAs.\n\n## Trust boundaries\n\n- security_controls.py validates evidence integrity; it does not authenticate the origin of raw laboratory data.\n- execution_gate.py accepts approval_attestation_verified only after an external trusted identity/signature layer verifies the attestation. An untrusted client setting a boolean does not prove identity.\n- Replay stores must be durable in deployment. An in-memory set is a unit-test mechanism only.\n- Hash chains provide tamper evidence, not non-repudiation. Production provenance should be signed or attested by a separate trusted service or hardware-backed key.\n- No control in V0.2 upgrades QPHONON from L2 architecture to L3 physical capability.\n\n## Standards alignment\n\nThe hardening profile is directionally aligned with NIST SSDF secure-development principles, OWASP CI/CD guidance on least privilege, protected review, secrets hygiene, integrity verification, and visibility, and the SLSA provenance model. These are external references; this repository does not claim certification or formal conformance.\n\n## Security acceptance\n\nThe hardening branch may advance only when all original QPHONON tests remain green, all V0.2 adversarial tests pass, CodeQL and repository-wide required checks pass, no secret is required by QPHONON CI, and PR #207's L2 physical-capability boundary remains unchanged.\n
