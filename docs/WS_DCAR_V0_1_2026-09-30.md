## Mission

WS-DCAR is a vendor-neutral assurance layer for data-center resource and flexibility commitments. It does not replace schedulers, DCIM/BMS platforms, DERMS, demand-response aggregators, or utility controls. Its role is to preserve and test the evidence required to determine whether a claimed event actually satisfied an authorized commitment.

## Trust chain

```text
request
  -> PRIME authorization
  -> SARA orchestration
  -> facility / compute / storage / cooling actuation
  -> ECHO SENTINEL LINK evidence and provenance
  -> OVERWATCH verification / disposition
  -> signed audit package
```

## Measurement model

The first reference gate distinguishes:

- `delta_P_grid`: instantaneous reduction at the grid boundary;
- `delta_E_grid`: event energy effect;
- workload reduction or migration;
- battery substitution;
- on-site generation substitution;
- HVAC contribution;
- rebound energy after the event.

Two events that both report "20 MW curtailed" are not assumed equivalent when their mechanisms, baselines, configuration state, authorization, provenance, or rebound differ.

## Evidence minimum

A field candidate should preserve at least:

- request source and request ID;
- timestamps with clock-source provenance;
- human/machine authorization state and authorization evidence;
- policy/configuration hashes;
- hardware, firmware and software manifest identity;
- baseline method and uncertainty;
- authoritative grid meter identity/provenance;
- command and measured-response timestamps;
- source decomposition;
- event duration;
- rebound energy;
- telemetry gaps and stale-data markers;
- operator overrides;
- exception disposition;
- evidence hash/signature and audit reference.

## FLEX-001

`research/ws_dcar_flex_001/` provides a standard-library reference verifier, time-series replay path, representative synthetic trace, external-surrogate adapter, and pytest regression suite.

The verifier can return only:

- `VERIFIED`
- `VERIFIED_WITH_EXCEPTIONS`
- `INSUFFICIENT_EVIDENCE`
- `NONCOMPLIANT`

The design intentionally refuses to collapse missing evidence into a pass/fail claim.

### Time-series assurance

The trace verifier additionally tests whether evidence remains coherent throughout an event. It detects:

- configuration drift and missing configuration custody;
- meter-identity changes and invalid meter provenance;
- stale telemetry and excessive gaps;
- missing request provenance;
- missing authorization evidence versus a known unauthorized action;
- late response or duration shortfall;
- generator substitution;
- mismatch between integrated grid-boundary reduction and the energy attributed to individual mechanisms.

This prevents an apparently correct aggregate result from masking an untraceable or materially different execution path.

## EXT-001 — external processed surrogate

The first external-format path is implemented in `research/ws_dcar_flex_001/external_surrogate.py`.

Declared source:

- repository: `bram-exe/PSCAD-Hypersim-Data-Center-Modeling`;
- path: `Training Load Simulation/pscad_load_short.csv`;
- Git blob: `693cb03b53af4d6fdeee72c88269c0e5dd0a48e9`;
- upstream measured-data DOI: `10.7799/3025227`;
- declared scaling: nominal 250 MW data-center load on a 5 GW system base.

The public source describes a Llama2-70B LoRA training-power trace derived from measured GPU telemetry, then transformed by summing device telemetry, subtracting its mean, scaling the variation to a nominal 250 MW data-center load, converting it to per-unit on a 5 GW base, and trimming a 300 s window.

WS-DCAR intentionally does **not** treat this as an authoritative grid-meter event. The adapter verifies the external Git blob identity, preserves an additional SHA-256 source hash and transformation metadata, performs the declared per-unit-to-MW mapping, and then marks the evidence fields that the surrogate cannot establish as invalid or unknown. Therefore its proper disposition is `INSUFFICIENT_EVIDENCE`, not `VERIFIED`.

This is an important validation result: useful third-party power data can be ingested without laundering modeled or transformed data into an unsupported field claim.

## External validation gate

Before any field-performance claim, validate with a partner dataset or sandbox that provides:

1. authoritative grid-boundary measurements;
2. known request/control commands and request provenance;
3. authorization evidence;
4. facility or workload mechanism telemetry where available;
5. synchronized timestamps and clock provenance;
6. configuration identity/custody;
7. documented baseline rules and uncertainty;
8. one or more injected or naturally occurring adverse cases.
