# Zenoh #2783 — metadata-only storage queries without transferring payloads

Upstream issue: `eclipse-zenoh/zenoh#2783`
Reviewed upstream main: `646f2d1b730e584a570015a77bee9f6db08be9d1`
Claims state: **SOURCE-REVIEWED FEATURE DESIGN / REQUIRES MAINTAINER API DECISION + RUST TESTING**

## What current source supports

The storage manager has a backend-independent interception point in:

`plugins/zenoh-plugin-storage-manager/src/storages_mgt/service.rs::reply_query()`

Both wildcard and non-wildcard query paths:

1. receive the `Query` centrally;
2. pass `q.parameters().as_str()` into the backend `Storage::get()`;
3. receive `Vec<StoredData>`;
4. build the outgoing query replies in the storage manager.

That means a first implementation can strip the payload **before wire serialization** without changing each RocksDB/filesystem/S3 backend.

## Important limitation discovered during source audit

Current `zenoh_backend_traits::StoredData` is:

```rust
pub struct StoredData {
    pub payload: ZBytes,
    pub encoding: Encoding,
    pub timestamp: Timestamp,
}
```

It does **not** contain the original sample attachment. `Storage::put()` likewise receives only key, payload, encoding, and timestamp.

Therefore the issue's proposed `original_attachment` cannot be returned faithfully by a phase-1 storage-manager-only change. Worldshepherd should not claim otherwise.

Supporting original attachments would require an explicit storage schema/trait evolution (and migrations/backward compatibility for durable backends), or a separate metadata side channel. That should be a later maintainer-approved phase.

## Recommended Phase 1 contract

Use a reserved selector parameter only after maintainers approve its spelling. The issue suggests `_meta_only=true`; this document uses that name provisionally.

For:

```text
get("camera/frame?_meta_only=true")
```

the reply should preserve:

- key expression;
- timestamp / HLC;
- encoding, if maintainers consider it part of metadata semantics;
- an empty payload on the wire;
- an attachment generated by the storage manager containing at least `payload_len`.

Example logical metadata, encoding format TBD:

```json
{
  "payload_len": 7340032
}
```

Do not overload the normal payload with metadata: keeping the reply payload empty makes the bandwidth-saving contract explicit and allows callers to distinguish metadata probes from ordinary stored values.

## Central implementation shape

Parse the reserved parameter once per query, then keep backend parameters semantically separate.

Conceptually:

```rust
let meta_only = q.parameters().get("_meta_only") == Some("true");
```

The actual parameters API should follow the repository's supported `ZenohParameters` interfaces; avoid brittle raw-string matching.

For each returned `StoredData`:

```rust
let payload_len = entry.payload.len();

let mut reply = q
    .reply(key, if meta_only { ZBytes::empty() } else { entry.payload.clone() })
    .encoding(entry.encoding.clone())
    .timestamp(entry.timestamp);

if meta_only {
    reply = reply.attachment(encode_metadata(payload_len));
}

reply.await?;
```

The above is architectural pseudocode, not compile-validated Rust.

## Do not blindly forward `_meta_only` to every backend

Today `reply_query()` forwards the entire parameter string into `Storage::get()`. A storage-manager-reserved parameter creates a namespace/compatibility question:

- existing backends may interpret unknown parameters;
- a backend may already use the same key;
- future backend query semantics should not accidentally depend on a manager-only option.

Preferred behavior is to parse/remove the reserved manager parameter before calling `Storage::get()`, then pass through all remaining backend parameters unchanged.

This needs a project-level decision on reserved parameter naming and parsing API.

## Phase 1 performance boundary

A central storage-manager implementation prevents the payload from crossing the Zenoh network, which directly satisfies the primary bandwidth problem.

It may **not** prevent the backend from reading the full payload into memory, because `Storage::get()` still returns `StoredData` containing `ZBytes`.

So claims must distinguish:

```text
Phase 1: avoids payload network transfer
Phase 2: may avoid backend payload read/allocation via backend metadata APIs
```

Do not describe Phase 1 as zero-copy metadata lookup.

## Phase 2 backend capability

If measurements justify it, evolve `zenoh_backend_traits::Storage` with an optional metadata operation or capability, for example conceptually:

```rust
async fn get_metadata(
    &mut self,
    key_expr: Option<OwnedKeyExpr>,
    parameters: &str,
) -> ZResult<Vec<StoredMetadata>>;
```

with:

```rust
struct StoredMetadata {
    payload_len: u64,
    encoding: Encoding,
    timestamp: Timestamp,
}
```

The exact API should be maintainer-designed because adding a trait requirement affects external backend implementations. A default fallback to ordinary `get()` could preserve compatibility while optimized backends override it.

## Original attachment support is a separate schema decision

To preserve original sample attachments end-to-end, the storage contract itself must store them. That would affect:

- `StoredData`;
- `Storage::put()`;
- memory backend;
- RocksDB backend;
- filesystem backend;
- S3 backend;
- serialization/migrations for existing durable stores;
- replication/alignment paths.

Do not fold this into the first metadata-only PR unless maintainers explicitly request the broader schema change.

## Required tests

Add storage-manager tests using the existing `plugins/zenoh-plugin-storage-manager/tests/operations.rs` infrastructure.

Minimum matrix:

1. ordinary get still returns the full payload unchanged;
2. `_meta_only=true` returns zero payload bytes;
3. metadata reports the exact original payload length;
4. timestamp equals the stored sample timestamp;
5. encoding behavior follows the accepted contract;
6. wildcard query returns metadata for each matching key;
7. empty payload returns `payload_len=0` correctly;
8. large payload test proves received payload is empty and avoids network-sized reply transfer;
9. reserved parameter is removed before backend-specific parameter handling if that design is accepted;
10. `_meta_only=false` behaves like a normal get;
11. malformed/duplicate parameter values have deterministic behavior;
12. no regression to replication/alignment queries.

## Worldshepherd relevance

This is directly useful for DDIL/robotics data planes containing images, maps, point clouds, and model artifacts. An assurance layer can check freshness/HLC and expected size before spending constrained bandwidth on a full transfer.

The architectural invariant is:

> **Use metadata to decide whether a large object is worth transferring, while preserving provenance and avoiding a second inconsistent key-space.**
