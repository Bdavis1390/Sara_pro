# QCRYPTO SARA → ECHO evidence synchronization

## Scope

The QCRYPTO runtime can synchronize one already-recorded, already-verified four-stage governance decision from SARA into ECHO SENTINEL LINK. This path is evidence transport only.

It does **not** execute a cryptographic migration, move value, sign blockchain transactions, grant live-value authority, establish Federal compliance, establish WS-CAE conformance, or make the current Ed25519 ECHO checkpoint post-quantum secure.

## Decision identity and audit-instance identity

Two identifiers are deliberately kept separate:

- `decision_digest` is the deterministic SHA-256 correlation value for the semantic decision content. Two identical decisions can have the same digest.
- `audit_instance_id` is generated by SARA for one concrete four-event audit submission. It has the form `QCRYPTO-AUDIT-<32-hex>` and is not accepted from the caller as part of the submitted decision projection.

This separation prevents two independently recorded but semantically identical decisions from being conflated during verification or ECHO synchronization.

## Preconditions

SARA requires the supplied `decision_digest` **and** `audit_instance_id` to reconstruct a complete and internally consistent set of exactly four canonical stages:

- ECHO provenance state
- PRIME recommendation state
- SARA human-governance state
- OVERWATCH tracking state

Incomplete, inconsistent, authority-escalated, malformed, or identity-mismatched evidence is rejected before any ECHO forwarding attempt.

## Runtime boundary

The synchronization endpoint is:

`POST /admin/qcrypto/audit/echo-sync?decision_digest=sha256:<64-hex>&audit_instance_id=QCRYPTO-AUDIT-<32-hex>`

The bounded verifier is:

`GET /admin/qcrypto/audit/verify?decision_digest=sha256:<64-hex>&audit_instance_id=QCRYPTO-AUDIT-<32-hex>`

Both paths are admin-only. SARA forwards the four canonical audit records to ECHO `/v1/ingest`, then requests `/v1/reconcile` for the same bounded SARA record set.

Successful QCRYPTO synchronization requires all four submitted event IDs to be explicitly classified `MATCHED`, with:

- `MATCHED = 4`
- `SARA_ONLY = 0`
- `PAYLOAD_MISMATCH = 0`

`ECHO_ONLY` is **not** required to be zero. ECHO is a persistent evidence store, so unrelated evidence retained before the selected QCRYPTO audit instance is expected to appear as `ECHO_ONLY`. QCRYPTO synchronization verifies its own four submitted event IDs rather than demanding that the entire ECHO store contain only those four records.

ECHO replay deduplication is accepted. A semantic conflict, missing submitted event, wrong reconciliation schema/scope, malformed reconciliation response, or mismatch in any submitted event fails closed. If ECHO is unavailable or not configured, SARA retains its durable local audit and records a pending synchronization event so the operation can be retried.

Synchronization bookkeeping uses `source_decision_digest` and `source_audit_instance_id`, not the canonical `decision_digest` field, so synchronization bookkeeping cannot become part of the original four-stage decision reconstruction.

## Deployment

The default SARA Compose service remains disconnected from ECHO. To enable the private bridge, use the base deployment together with `compose.qcrypto-echo.yaml` and the ECHO profile. The overlay:

- attaches SARA to `echo_private`;
- sets `ECHO_PERSISTENCE_URL=http://echo:9550`;
- mounts the ECHO ingest credential into SARA read-only at a separate path;
- does not expose ECHO private storage or checkpoint signing keys to SARA.

The forwarder permits cleartext HTTP only for loopback or the local Compose service name `echo`. Any off-box endpoint must use HTTPS. The forwarding credential must be an owner-controlled regular file with no group/other permissions and must be independent of SARA and PRIME credentials.

## Validation and evidence classification

The deployed bridge gate exercises an isolated SARA/ECHO Compose project, seeds unrelated retained ECHO history, submits a real QCRYPTO decision through SARA, synchronizes the selected four-event audit instance, repeats synchronization to test deduplication, re-verifies the original SARA chain, and creates an ECHO checkpoint.

A specific software revision may be labeled **PROVEN INTERNALLY** for this bounded behavior only when the QCRYPTO Risk Gate, QCRYPTO ECHO Bridge Gate, and full SARA Verified Local gate are green on that exact revision. A prior green revision does not automatically validate later changes.

Even after internal proof, the following remain outside the claim:

- production deployment;
- migration execution or transaction signing;
- live-value authorization;
- post-quantum security of the current Ed25519 ECHO checkpoint;
- external or third-party attestation;
- Federal compliance;
- WS-CAE conformance;
- partner or physical-system validation.
